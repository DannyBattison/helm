## 2026-10-27 · Continuous sync between instances
Builds the plan in `2026-10-27-manual-sync-between-instances` (this supersedes its manifest/rules where they differ). Per server, "Keep in sync" keeps a standing WebSocket (`/api/sync/stream`, key sent in the first message, 429-limited per address) and syncs by itself; the manual button still works and uses the same code.
- The socket is only a doorbell. The server sends `changed` (debounced) when its data changes or when it applied a sync that changed something; the starting side syncs on the ring, 2 s after its own changes (`Store.onLocalChange`), on connect, and every 5 minutes as a safety net. All data still moves over the HTTP manifest/pull/push calls, so there is one path to get right. Reconnects back off 1 s → 60 s. Regenerating the key or turning syncing off hangs up connected instances.
- Records (sessions, repos, automated agents) carry `updatedAt`, stamped by `Store.flush` when a record's content (minus `lastAccess`) differs from the last look; the later copy wins. A sync-applied record is marked so it is not counted as an edit and does not echo. A repository keeps this machine's `localPath`.
- Deletions are tombstones (`data.deleted`, 30 days). A record changed after its deletion is kept and wins.
- Transcripts are compared by event count and content hash, and sent from 50 events before the end, because a tool result is patched into an earlier slot. On equal length the side whose session changed last wins. A session running on an instance is owned by it: others never overwrite it, and their copy shows `remoteOwner` ("Running on <host>"), idle, and refuses `send` until the owner stops it.
- Not done: opt-in per kind of data (it is per server only), and no change cursor (the manifest is compared in full each time; cheap because it is ids, counts and hashes, with transcript hashes cached by file size and mtime).
Why: user request.
