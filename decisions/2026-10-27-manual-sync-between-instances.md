## 2026-10-27 · Manual sync between helm instances
Settings → "Import, export and sync" has a Sync section. A sync is started by one instance (button: "Sync all history", or per server) and talks plain HTTP to the other: `GET /api/sync/manifest`, `POST /api/sync/pull`, `POST /api/sync/push`, authorised by `Authorization: Bearer <sync key>` (`src/core/sync.ts`, `src/shared/sync.ts`, routed in `hosted/src/server.ts` before the cookie gate).
- Only a hosted server has an address, so only it can be synced *into* (the "Let other instances sync with this one" switch and the key are shown there, `syncEnabled` off by default; off means the routes answer 404). The desktop app can start syncs to any number of servers (name + URL + key pairs) but cannot receive. Desktop↔cloud and cloud↔cloud work; desktop↔desktop does not. One desktop can sync with several clouds, and each cloud with another, because the diff is always "what does each side lack", never a one-way mirror.
- The key (`hsk_…`, regenerable) and the list of servers with their keys live in `sync.bin`, encrypted by the host like the other secrets and never exported. Failed key guesses are rate limited per address.
- Diff: each side sends a manifest (repo ids, automation ids, per-session transcript bytes and last-event time, content hashes of usage/audit/daily records, repository artifact paths). A session is copied when the other side lacks it or is further behind (more transcript bytes; on a tie, later event; merely viewing a session doesn't count). The receiver re-checks and never replaces a session that is running there. Machine-local fields (worktree, worktreeGone, extras, uploads) of an existing session are kept; new sessions come in idle and flagged `worktreeGone` if their folder isn't here.
- Not synced: settings, sign-ins, passwords, the user, the activity log, lifetime totals, caches, worktrees themselves (the git branches are the way code moves). Repos arrive with the other machine's `localPath`. Nothing is deleted, so a session removed on one side returns on the next sync.
Why: user request. Manual only, because a pull/push over a plain manifest diff is simple and safe to repeat.

## Plan for continuous sync (not built)
1. Change tracking: give sessions, repos and automations an `updatedAt` plus an `origin` instance id, bumped in one place (the store's change hook), so "newer" no longer relies on transcript size and renames/archiving sync. Give each instance a stable `instanceId`.
2. Tombstones: a `deleted: {kind, id, at, origin}` list so deletes propagate and don't resurrect; pruned after e.g. 30 days.
3. Transcripts as an append log: sync by `(sessionId, fromIndex)` so a live session streams only new events instead of whole files; a transcript has one writer (the instance running it), so there are no merge conflicts. Take a session "lease" (owner = instance id) so the other side shows it as read-only/"running on X" and cannot resume it until released.
4. Transport: the initiator keeps a WebSocket to each peer (`/api/sync/stream`, same bearer key), sends a cursor (per-peer high-water mark of change sequence numbers) on connect to catch up with the manifest diff built here, then streams changes both ways. A desktop behind NAT works because it dials out; a cloud-to-cloud pair needs one side to dial.
5. Conflicts: records with one writer (sessions, transcripts) need none; shared records (repos, automations, budgets) use last-writer-wins on `updatedAt` with the instance id as tiebreak. Usage ledgers are already append-only unions (hash-deduplicated; give each record an id so they can be compared cheaply).
6. Also needed: per-peer opt-in per data kind, backoff and reconnect, a "last synced / lag" indicator, bandwidth limits for large artifacts, and a protocol version in the handshake. Key rotation should close live streams.
